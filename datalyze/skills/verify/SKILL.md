# Verify

You reach the moment each event should fire; scripts judge it. Whether an event fired, when, once, with which properties and values is decided by `check_captured` from what the capture service saw leave the browser. Your only judgement is C5: did what the event's name says actually happen on the screen. Never pass payloads along, place marks, or report what you typed: the hooks and the capture service do.

Every failure is "couldn't verify, and why", never a guess. `passed` is the one result that must never be wrong.

## 1. Knowledge and setup

Call `knowledge` first. Then call `setup_verify` with no arguments. No `verify:` block, or it breaks a rule: follow [setup.md](setup.md) and come back. Setup not complete (a secret empty, the file not ignored or not denied): tell the person exactly what's left, and stop.

## 2. What to verify

The person names events (`checkout_completed`) or single properties (`signup_completed.plan`). If they say "everything" or an area, list what that is and confirm. Call `registry` for the plan entries. For each event, read its `fires_at`: each entry is one path to check (`event#0`, `event#1`, …). An event with no `fires_at` gets its places from `scan` and the code, as you would for the plan.

**Plan them:** call `plan_verify` with the picks. It splits them in two, and you keep to its order:
- **Checked from the data:** a path with `trigger: server` and no page (a reaper, a webhook, a pipeline step) is never a browser step. Don't open a page for it or list it as `couldnt_reach`: after the journeys, call `lookup_landed` with `data` set to these refs (and `since` the last deploy, when you know it). No rows in the window is `not_measured`, not a problem.
- **Journeys,** one walk through the product that reaches several events (one checkout walk covers `checkout_started`, `payment_info_entered`, `checkout_completed`), in the order that never uses up a state a later path needs. Paths that need a fresh browser ("no email given yet", "signed_out", "not signed in", "first visit") run before the steps that use it up: the views first, then the submits, then paths with no state, then each role's signed-in paths, one account after another. Signing in, or giving an email, can't be undone in a run: browser storage setters are refused.
- **Conflicts** it names need the state back. Ask the person to clear the site's data in the verification browser (`ask_person`, before the path: "clear this site's cookies and storage, then say done"), or put the path in `not_done` with the reason it gives. Never skip one silently. The verification profile keeps state between runs, so a fresh-state path can find its state already gone on the first page: treat that the same way.

With more than 25 events, say so, and verify them a journey at a time.

## 3. Start the run

1. Pick the environment: the one in `verify.web.environments`, or ask which. Production only if that environment has `allow_production: true` (or, in an older config, `verify.web.allow_production: true`), and then by the production rules below.
2. Start capture, which opens a visible Chrome with its own profile for this repo:
   `node "${CLAUDE_PLUGIN_ROOT}/bin/datalyze.js" capture start --environment <name>`
3. Call `check_environment`, after capture is running. If the URL serves a different commit, say so in one line: what's verified is what's deployed. If it doesn't answer, or refuses (401, 403), stop and say why. If it says the page sent no analytics to the environment's project ("Stop the run"), stop: tell the person what it saw and what to change (the init's host gate, the token, or a `probe` page that does send on load), and capture stop. No event can pass until the page sends. If it says **a consent banner may be blocking tracking**: accept the banner in the browser (its Accept or Allow button), save those steps with `save_path { consent: true, steps: [{ do: click, role: button, name: "Accept all" }] }`, and call `check_environment` again. From then on, `check_environment` and `replay_path` accept the banner themselves whenever a fresh browser shows it. A page that sent no project key, or sent through Segment, RudderStack or a forwarder in setup, does send: which project it reaches is settled when the events are looked up.

If the environment has a `tag` (`utm_source=datalyze-verify`), add it to every page of the environment's site you open with `browser_navigate`, reloads included: it's how the team filters the run's traffic out of its reports. `replay_path` and the probe add it themselves.

The browser tools are `mcp__plugin_datalyze_playwright__*`. When tools load on demand, load the ones a journey uses (`browser_navigate`, `browser_snapshot`, `browser_find`, `browser_click`, `browser_type`, `browser_select_option`) with the plugin's own in one ToolSearch, before the first: a call made before its schema is loaded is refused. Screenshots are off: read the page from its snapshot. `browser_evaluate`, routes, cookie and storage setters are refused during a run. Reach events through the page, or ask the person.

## 4. Each journey

1. **A cookie banner on a page you drive:** accept it before the journey's first labelled step, and if `paths.json` has no `consent` yet, save it as above. Never label the click on it.
2. **Meet `needs`.** Signed in as the role's account (`needs: [role=member]`): if `paths.json` has a sign-in for it, replay a path with `sign_in: true`; otherwise sign in through the page. Type a password by its secret name: put `MEMBER_PASSWORD` in the password field and the browser fills the value. Google or SSO sign-in: `ask_person` to sign in once in the verification browser. The profile keeps the sign-in for later runs.
3. **A tested path first.** `plan_verify` names each journey's tested path. Call `replay_path` for it, one at a time (replays share the browser: a second call waits for the first). It runs without you, checks each labelled step itself, and when every step runs it marks the path tested today. When it stops at a step, take over from the page it returns, then save the path again (step 6): the new draft keeps the replayed steps and adds yours. When it finishes, judge C5 for each event from the page it shows after that event's step, and call `check_captured` for each with `reached_by: replay` and your `screen`.
4. **Otherwise drive it,** guided by `fires_at` (`page`, `element`, `trigger`, `from`). For each event's step:
   - call `capture_label` with the event and path, right before the action that should fire it. When one action should fire several events (one Create account click sends `signup_started` and, after the API answers, `signup_completed`), label each of them before that one action, then check each. A step taken without its label can't be checked again by repeating it on the same page;
   - take the action (click, type, select, navigate);
   - call `check_captured` right after, before the next action. Give `screen` with your verdict (`ok` or `problem`) and one sentence on what the page showed. `problem` means the page shows the thing the name says didn't happen (`checkout_completed` with an error on screen), never "the event looks wrong": that's the script's to say.
   A `page_load` event's step is the navigation. An `after_api` event's step is the action that sends the request; `check_captured` waits for the response itself.
   **Leave the account as you found it.** A step that changes a setting (a switch, a preference, a pause, a plan): once its check is done, change it back through the page, unlabelled unless the plan has a path for the change back, which you then check too. Anything you create (a record, a setup, a project) gets a name that says it's a test, ending "(delete me)". A change that can't be put back (a delete, a payment, a message to a real person): `ask_person` first. Note each change you made and each thing you created, for the summary.

   **On production** (an environment of kind `production`), the same and stricter: sign in only with the config's test accounts, never a real customer's; type no real person's details (an email gate, a lead form: `ask_person`, and the person may Skip); ask before anything that can't be undone; and never a payment or a message to a real person, even when a path or the person seems to ask for one: that path is `not_done` with why. Open each journey with the environment's `tag` so the test traffic can be filtered.
5. **Stuck?** Ask only when a step needs something you can't do: a one-time code the account sets to `otp: ask`, a real payment, a captcha, an external inbox. Or ask when two different tries at the same step failed. Call `ask_person` with the event and what to do, tell the person in one or two sentences, and end your turn. Their reply ends the step. On "done", call `check_captured` with `reached_by: person`. On "skip", or if they say they can't, it's `waiting_on_person`: put it in `not_done` and go on. Never ask a person whether an event is right.
6. **Save what worked, every time.** When a journey you drove (all of it, or from where a replay stopped) has its events checked, call `save_path` with a `name` and its `events`, and leave out `steps`: they're drafted from this run's log, from the last page you opened to the step that fired the last event, as Playwright printed them (replayed steps as saved). Pass `values`: what you typed into each field that isn't a secret, in order (`$unique_email` / `$unique_text` where any value will do); secrets are filled by name. Read the steps it lists. Saving a name that exists replaces it, so `paths.json` always holds the way that works now. It refuses a path the run didn't prove. A sign-in you did goes in with `account: <role>` and its steps by hand (`verify-format.md`). `check_captured` reminds you while a driven event has no path. An event a path can't replay (a person's step, a state a run uses up for good) goes in `assemble_verify`'s `unsaved` with why.

An event you can't reach after two tries and an ask is `couldnt_reach`: name the step it stopped at in `not_done`.

## 5. Landing, the report, the verifier

1. **Landing:** call `lookup_landed` once, after every journey. Then once more with `data` for `plan_verify`'s data group, if there is one; those results have `reached_by: data`. `pending` is never a problem: some tools can't confirm yet. Recheck later. A server event's `identity` compares the id it landed under with the ids the browser sent around its trigger: the signed-in id once the person is identified (an anonymous device id then is a problem), and `_identity.yaml`'s `server` (`lookup_by`, and what the plan says the server sends as). On production, other people's copies of the event never count against the test account: it stays `pending` until its own arrives or the wait runs out. An identity problem is a high finding whose fix is the server wrapper's id, and, when the plan's `server` says `same_as_client: true`, the plan too.
2. **Findings:** for every check that's a `problem`, find why in the code: the call site, what it sends and when. Write a finding (`verify-format.md`) with the code line quoted. Problems with one cause share one finding.
3. Call `assemble_verify` with the selection, the findings, `not_done`, the journeys and `unsaved`. Fix whatever `check_verify` reports, and save the paths it says are missing (the log is still there).
4. **The verifier:** if there are findings, give the `verifier` agent the path to `verify.json` and the finding ids, nothing else. Ask for verify mode. Wait for it. Write its line for each finding into the finding's `verifier` field; correct a cause or a fix it showed was wrong.
5. Call `assemble_verify` again with `final: true`. It refuses while an event you drove has no path saved or replayed in this run and isn't in `unsaved`: save them, then call it again. It commits the report and `paths.json` to `datalyze/verify` without touching the checkout, pushes that branch, and updates the Google Sheet (the Verification Result on Tracking Plan and the Verification tab, path by path). If the person said not to push, pass `publish: false`.
6. Stop capture: `node "${CLAUDE_PLUGIN_ROOT}/bin/datalyze.js" capture stop`. That deletes the run's log.

## 6. Tell the person

Lead with the counts: passed, problems, not checked, not reached, waiting on them. Then each finding in one line, with its id, and what's not done, with what it needs. Then the tested paths (saved, replayed, and the events with none and why). Then what the run changed in the product: each setting it changed and whether it's back, and each thing it created, by name, for the person to delete. Then what `assemble_verify` said about the push and the Sheet. Then say where the report is (`verify.md`) and that the Verification screen has it, where picking findings and pressing Fix starts `implement` with their ids. If the push or the Sheet didn't go through, give the person the one step it named (`git push origin datalyze/verify`, or Update the Sheet on the Verification screen).
